# FlavorFit — клиент

Приложение для подбора рецептов под дневную норму КБЖУ. Пользователь заполняет замеры тела и цель, приложение считает норму, подбирает под неё рецепты и собирает список продуктов на закупку.

Проект в работе: готовы авторизация, профиль с замерами и лента рецептов. Расчёт нормы и корзина — следующие по плану.

Сервер: **[FlavorFit-backend](https://github.com/muhammad2008nur/FlavorFit-backend)**

## Токены

`localStorage` — самое частое место для JWT и самое плохое. Любой скрипт на странице его читает: подключённая аналитика, зависимость, которую подменили в npm, вставка через XSS. Токен уходит целиком, и вы об этом не узнаете.

Здесь их две штуки, обе в куках с `httpOnly`. JavaScript их не видит вообще — браузер сам прикладывает к запросам. Access живёт час, refresh три дня.

Когда access протухает, сервер отдаёт `UNAUTHENTICATED`. `ErrorLink` в цепочке Apollo перехватывает эту ошибку, запрашивает `newTokens` и повторяет запрос, который упал. Пользователь ничего не замечает.

При переходе на закрытую страницу то же самое делает `proxy.ts` (так в Next.js 16 называется бывший `middleware`). Если access-куки уже нет, а refresh есть, он сам получает новую пару и отдаёт куки вместе с ответом — страница рендерится уже с живой сессией, без редиректа на вход. Подпись access-токена проверяется прямо в proxy через `jose`, без похода на сервер. Поэтому клиенту нужен тот же секрет, что и серверу.

## Apollo в браузере и на сервере

Клиенты разделены: у браузерного свой кэш с политиками для ленты, серверный работает в `ssrMode`.

Но серверный пока создаётся один раз на весь процесс Node, а значит, и `InMemoryCache` у него один на всех пользователей — профиль первого пользователя может уехать второму. Сейчас от этого спасает `fetchPolicy: "no-cache"`, но это костыль. Правильно — создавать новый клиент на каждый запрос.

## Лента рецептов

Пагинация по курсору, а не по номерам страниц. Почему так — расписано в [README сервера](https://github.com/muhammad2008nur/FlavorFit-backend#лента-рецептов). На клиенте из-за этого две задачи.

**Собрать курсор.** Он зависит от сортировки: для «новых» это дата, название и `id` последнего рецепта, для «популярных» — просмотры, для «рекомендованных» — лайки. Смотри `getCursor` в `features/recipes/ui/Recipes.tsx`.

**Склеить страницы в кэше.** В `typePolicies` у `feedRecipes` ключ кэша — только `sort` и `searchTerm`, курсора в нём нет. Поэтому все страницы одной сортировки ложатся в один список: `merge` дописывает новую страницу в конец и выкидывает дубли по `id`. Другая сортировка — другой ключ и другой список. Старый остаётся в кэше, и при возврате к той сортировке Apollo берёт его оттуда.

## Формы

Профиль — одна форма с режимами просмотра и редактирования на react-hook-form. Все правила лежат в одной Zod-схеме `features/profile/profile-schema.zod.ts`: пустые строки превращаются в `null`, числа из инпутов приводятся и проверяются по диапазонам, желаемый вес не может отличаться от текущего больше чем на 100 кг.

Логика формы вынесена в хук `useProfileForm`, компоненты только рисуют. Селекты Radix подключены через `Controller`, список ссылок — через `useController`.

## Структура

```
src/
├── app/            # роутинг, провайдеры, глобальные стили
├── features/       # auth, layout, profile, recipes
│   └── profile/
│       ├── graphql/    # запросы и мутации фичи
│       ├── hooks/
│       └── ui/
├── shared/         # переиспользуемое между фичами
│   ├── api/            # сгенерированные типы GraphQL
│   ├── lib/apollo/     # клиенты и links
│   ├── lib/server/     # чтение и проверка токенов для proxy
│   ├── config/
│   └── utils/
└── proxy.ts        # защита закрытых страниц
```

`features` тянут из `shared`, обратно — нет. Смысл в том, что любую фичу можно вырезать целиком, не разбирая, за что ещё она держится.

Друг о друге фичи не знают, с одним исключением: шапка в `layout` берёт кнопку выхода из `auth`. По FSD шапке место в слое `widgets` — перенесу.

## Запуск

Нужен Node 20+ и поднятый [сервер](https://github.com/muhammad2008nur/FlavorFit-backend).

```bash
git clone https://github.com/muhammad2008nur/FlavorFit.git
cd FlavorFit
npm install
cp .env.example .env
npm run dev
```

Открыть `localhost:3000`. Порты лучше не менять: CORS на сервере пока пускает только `localhost:3000`, а картинки в `next.config.ts` разрешены с `localhost:4200`.

| Переменная | Описание |
|---|---|
| `NEXT_PUBLIC_SERVER_URL` | адрес сервера без `/graphql`, например `http://localhost:4200` |
| `NEXT_PUBLIC_CLOUDFLARE_SITE_KEY` | публичный ключ Turnstile. Локально подойдёт тестовый `1x00000000000000000000AA` — он всегда пропускает |
| `JWT_SECRET_KEY` | тот же секрет, что `JWT_SECRET` на сервере: им proxy проверяет подпись access-токена |
| `GRAPHQL_SCHEMA_URL` | откуда codegen берёт схему, по умолчанию `http://localhost:4200/graphql` |

Типы запросов руками не пишутся — `npm run codegen` собирает их из схемы сервера. Гонять после каждой правки схемы, иначе TypeScript будет врать.
